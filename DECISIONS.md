## Phase 7 — Legal, SEO, accessibility, performance, tests

**The brief's own suggested "safe" teal for text (`#2E948C`, i.e. what the codebase calls `--emc-teal-600`) fails WCAG AA.** Section 13 flags the raw teal as "borderline for small text" and says to "use `--emc-teal-600` or darker for text" — but measured, `--emc-teal-600` on white is only 3.66:1, below the 4.5:1 body-text minimum (it does clear the 3:1 bar for large text/icons/UI components, which is the reserved use Section 13 also describes). Added a new `--emc-teal-700` (`#28817a`, same hue/saturation, darker — 4.65:1 on white) and swapped every *text* usage of `text-emc-teal-600` (eyebrows, "Learn more" links, nav active state, leader-card titles — 26 lines across 22 files) to `text-emc-teal-700`, via a script that left every icon usage (`aria-hidden="true"` lines — MapPin, Phone, CheckCircle2, etc.) on `text-emc-teal-600`, since those only need the 3:1 non-text bar and are a deliberate lighter accent per Section 6.1. Also repointed the global `--ring` token (used for every `focus-visible` state sitewide) from `--emc-teal-400` (2.27:1 — nearly invisible) to `--emc-teal-700`.

**The mega-menu's keyboard focus ring was genuinely near-invisible, not just borderline — found by testing real keyboard Tab, not just computing token contrast.** Every other interactive component (Button, Input, Select, Textarea, Accordion, Badge) pairs a soft `ring-ring/50` glow with a solid `border-ring` layer, so darkening `--ring` alone was enough to fix them. `navigation-menu.tsx`'s trigger and link styles are the one component without that solid layer — they rely on `outline-1` with no explicit outline color utility, which (per live DOM measurement) rendered as the *same* 50%-opacity ring color as the glow: ~2:1 on white, well under the 3:1 focus-indicator minimum. Fixed by adding `focus-visible:outline-ring` (full opacity) alongside the existing `outline-1`, matching the pattern `tabs.tsx` already used for the same reason. Verified live via claude-in-chrome: real keyboard Tab onto the "Solutions" trigger now shows a crisp, clearly-visible teal outline (confirmed both visually via screenshot and via `getComputedStyle` + `:focus-visible` match).

**Form errors are now doubly wired for screen readers, not just visually shown.** `FormField` (`src/components/ui/form-field.tsx`) already put `role="alert"` on the error text (announces on appearance), but nothing linked the *input* to that message — a user tabbing back into an already-invalid field would get no announcement. Added `aria-invalid` + `aria-describedby` via `cloneElement` on the field's single child (covers every plain `Input`/`Textarea`/file-input field for free), plus the same two attributes hand-added to the three `Select`-based fields that go through `Controller` instead of a cloneable child (Contact's inquiry type, Demo modal's contact method, Quotation modal's procurement type — `cloneElement` can't reach through `Controller`, which doesn't forward unknown props). Verified live: submitting the empty Contact form sets `aria-invalid="true"` and `aria-describedby="name-error"` on `#name`, correctly pointing at the `role="alert"` paragraph.

**Base UI's Dialog (Request Demo / Quotation modals) already meets the keyboard/focus-trap/modality bar with zero custom code** — confirmed live: opening a modal auto-focuses its first field, every background element gets `aria-hidden="true"` (Base UI's modality technique in place of `aria-modal`, an equally valid ARIA pattern), Escape closes it, and focus correctly returns to the trigger button afterward. No fix needed; noting this so a future pass doesn't re-litigate it.

**The Playwright suite (Section 4) runs against a production build, not `next dev`.** First attempt used `next dev` (faster to boot) and hit a wall: nav-link clicks intermittently did nothing — no navigation, no error — while axe-core caught a teal eyebrow mid-fade-in at 1.95:1 contrast. Both traced back to the same root cause already logged in Phase 4's decisions: this repo's `next dev` fires unprompted Fast Refresh rebuilds that can swap out a component instance mid-interaction. Fixed by pointing `playwright.config.ts`'s `webServer` at `next build && next start` instead, and separately by setting `contextOptions: { reducedMotion: "reduce" }` so `Reveal`/`RevealGroup` skip their fade transition entirely (they already branch on `useReducedMotion()`) — both together made every run deterministic, dropping total suite time from ~90s with 10 flaky failures to ~58s with a clean pass.

**axe-core found one real, narrow contrast failure the earlier "teal-700 on white" fix missed: teal-700 on `--emc-gray-50`.** `bg-emc-gray-50` (`#f7f8fa`) is the site's alternating-section background, used on `about`, `home`, `partners`, and elsewhere — it's barely darker than white, but just enough that teal-700 (`#28817a`, 4.65:1 on pure white) measured 4.38:1 on it, under the 4.5:1 line. Recomputed a slightly darker value on the same hue/saturation that clears 4.5:1 against *both* `#ffffff` and `#f7f8fa`: `--emc-teal-700` is now `#277d76` (4.91:1 on white, 4.62:1 on gray-50). Small enough a shift it's not visually distinguishable from the original, but it's the number that actually matters. This is exactly the kind of gap a single-background contrast check misses and a real page-wide axe scan catches — reinforces that the accessibility pass (Task #41) and the Playwright/axe suite (Task #43) genuinely needed to both happen, not just one.

**Two selectors needed fixing for reasons that turned out to be correct app behavior, not bugs:** (1) the header's language switcher (`Button` rendered as `<Link>`) has `role="button"` in the accessibility tree, not `role="link"` — Base UI's `Button` stamps that role onto whatever element it renders as, which is the right call given it visually/behaviorally reads as a button, not a content link; tests now query `getByRole("button", ...)`. (2) the footer turned out to have its own copy of the language switcher (previously unknown to this pass), so the header one needed `getByRole("banner").getByRole(...)` scoping to avoid a strict-mode ambiguity — a legitimate site behavior (deliberate redundant access to language switching), not something to change.

**A real Lighthouse score could not be measured in this environment.** `npx lighthouse` requires a network fetch to install (this sandbox has no outbound network access — confirmed via a direct `curl` to the npm registry timing out), and no Lighthouse binary was pre-installed. In its place: ran a full `npm run build` (succeeded cleanly this time — see the memory note above — 65 static pages, all routes) followed by `next start`, and audited the real production network waterfall via claude-in-chrome (`read_network_requests`) on the home page: 2 CSS files, ~13 split JS chunks (Next.js's automatic per-route code-splitting), 2 font files, and exactly one image request (the header logo, served through `next/image`, cache-hit 304 on reload) — no render-blocking third-party scripts, no unoptimized assets. Combined with the already-in-place practices below, this is the best verification available here; a real Lighthouse run (Chrome DevTools locally, or CI) should still happen before launch and is called out again under Task #44.

**Section 13's performance asks were already satisfied by existing choices, not newly added:** `next/font/google` (`src/lib/fonts.ts`) sets `display: "swap"` on all 3 fonts and Next.js auto-generates size-adjusted fallback fonts for each — covers the "avoid layout shift from web fonts" ask with zero extra code. The only two `<Image>` usages (header/footer logo) already have explicit `width`/`height` (no CLS) and the header one is `priority` (above the fold) while the footer one correctly isn't (below the fold, shouldn't eager-load). The Contact page's Google Maps embed already had `loading="lazy"`. `Reveal`/`RevealGroup` (the sitewide scroll-animation wrapper) already animate via Framer Motion's `whileInView` (IntersectionObserver-driven, not eager-on-load) and already respect `prefers-reduced-motion`. No hero photography exists to "optimize" — the hero visual is `GradientMesh`, pure CSS gradients, zero image weight.

**`next-themes` and the shadcn `sonner` (toast) component are unused dead weight in `package.json`, left in place.** Neither is imported anywhere in the render tree (`components/ui/sonner.tsx`'s `Toaster` is never mounted; `next-themes` has zero imports repo-wide) — confirmed via grep and via the production network audit above showing no theme/toast-related JS chunk. Since Next.js only bundles what's actually imported, this costs nothing at runtime; removing the packages from `package.json` would be pure housekeeping, out of scope for a performance pass, so left as-is rather than risk touching unrelated files.

**SEO metadata is sourced from each page's own existing content field, not new marketing copy.** `buildMetadata()` (`src/lib/seo.ts`) is now called from every page's `generateMetadata`, with `description` derived from a field the page already renders (e.g. `product.shortDescription`, `content.intro.body`, `partner.summary`) via `truncateDescription()` (160-char, word-safe cutoff) — rather than writing fresh description copy per page, which would risk drifting from or contradicting the verified content itself. `Organization` JSON-LD (home), `Product` JSON-LD (product detail pages, deliberately with no `price`/`offers` per Section 9.4's no-cart rule), `Article` JSON-LD (Knowledge Center detail), and `BreadcrumbList` JSON-LD (every interior page, injected once from `PageBreadcrumb`'s existing `trail` prop) round out Section 12. `app/sitemap.ts` and `app/robots.ts` enumerate every static route plus all content-driven slugs (solutions/products/partners/jobs/news) across both locales via `alternates.languages`, disallowing only `/api/`.

## Phase 5 — Lead generation

**No `RESEND_API_KEY` is configured in this environment, and none was fabricated.** `src/lib/leads/dispatch.ts` checks for the env var at module load; if it's absent, email sending is skipped with a console warning but the lead is still durably written to `data/leads/*.jsonl` first — a submission never fails just because email isn't configured. `.env.example` documents `RESEND_API_KEY`, `LEADS_TO_EMAIL` (defaults to `info@tamiozmed.com`, Section 2.1's one verified inbox), and `RESEND_FROM_EMAIL` (defaults to Resend's own sandbox sender `onboarding@resend.dev`, which works with zero setup for testing but must be swapped for a verified sending domain before launch — flagging this explicitly since a wrong "from" address is an easy way to land in spam).

**Local JSONL storage is a dev/interim durability layer, not a production data store.** Section 11 explicitly allows "local JSON/DB store," so this isn't a deviation, but it's worth flagging: `data/leads/*.jsonl` lives on the server's local filesystem, which is ephemeral on Vercel (wiped on every redeploy) — fine for local development and for validating the form flows now, but Phase 7/8 (or whenever this ships to Vercel) needs either a real database or confirmation that email delivery alone is trusted as the record of truth. Noting this now so it isn't mistaken for a finished requirement.

**Two more Base UI gotchas caught in QA, both fixed at the pattern level so they don't recur:**
1. Passing a fully-formed `<Button {...} />` element through a component prop (e.g. `triggerButton={<Button size="lg" variant="outline" />}`) and using it as `DialogTrigger`'s `render` target silently drops the trigger's children — the button renders with no visible label at all. The same JSX written *inline* inside the component (`render={<Button size="sm" />}`) works fine. Root cause not fully isolated (looks like a `render`-prop children-merge quirk specific to prop-drilled elements vs. inline ones), but the fix is straightforward: `DemoRequestModal` and `QuotationRequestModal` now take primitive `variant`/`size`/`className` props and always construct the `<Button>` element inline themselves, rather than accepting a caller-built element. Caught because two "Request a Demo" buttons (home hero, product/solution pages) and the sitewide "Request a Quotation" button all rendered blank until this was found via DOM inspection (a stale-screenshot false alarm from earlier in the session had conditioned me to distrust the visual and check `textContent` directly — that's what caught this one, which was real).
2. `Select.Value` (bare `<SelectValue />`) doesn't auto-resolve a translated label from the selected value — same issue as the Phase 4 product-filter fix, just missed on three more selects (Contact page's inquiry type, Demo modal's preferred contact method, Quotation modal's procurement type). All three showed the raw English enum value (`general`, `email`, `direct`) even on the Arabic pages. Fixed with the same `children` render-prop pattern as Phase 4. Worth remembering as a standing rule for this registry: **`SelectValue` always needs an explicit children function, never bare.**

**Demo Request and Quotation Request modals accept a `defaultInterest`/`defaultProduct` prefill** when opened from a solution or product page, instead of only being reachable as a blank form from the header — a small UX improvement within what the spec already asks for (the modal "reachable from the header on every page"), not a new requirement.
